# Impunity

Networked multiplayer save-game and distributed object library for Unity. Provides TCP networking, a key-value document database, and real-time state replication via channels and entities.

## Repository Structure

| Directory | Target | Description |
|-----------|--------|-------------|
| `ImpunityCodeGenerator/` | netstandard2.0 | Roslyn source generator — produces serialization helpers for distributed entity types |
| `ImpunityRuntime/` | netstandard2.1 | Core shared library (networking, serialization, game state) — used by both client and server. This is just the project file to build the dll, the actual code lives ImpunityUnity/Assets/Scripts/Impunity for ease of testing in Unity |
| `ImpunityStandaloneServer/` | net10.0 | ASP.NET Core standalone server with WebSocket + TCP transport, can host multiple Impunity server instances |
| `native/libdatachannel/` | C/C++ (CMake) | `build.sh` builds the pinned libdatachannel + Mbed TLS into one shared library for the current platform and writes it, with a manifest, to `ImpunityStandaloneServer/runtimes/<rid>/native/` (committed binaries for osx-arm64, linux-x64, linux-arm64 and win-x64; rebuilt by `.github/workflows/native-libdatachannel.yml`; on macOS a copy pulled through Sourcetree or a browser is quarantined and will not load until `xattr -dr com.apple.quarantine ImpunityStandaloneServer/runtimes`). Loaded by the standalone server's WebRTC transport (`ImpunityStandaloneServer/src/webrtc/`) |
| `ImpunityTests/` | net10.0 | NUnit test project runnable with plain `dotnet test` — compiles the shared test sources against the non-Unity runtime; also hosts the out-of-proc standalone-server transport tests |
| `ImpunityUnity/` | Unity 6 (netstandard2.1) | Unity project containing client connection code, distributed field types, and test scenes |

Server-side game state code lives in `ImpunityUnity/Assets/Scripts/Impunity/Server/` and is linked into `ImpunityStandaloneServer` via glob includes in its `.csproj`.

## Build

```bash
# Build everything (CodeGenerator → Runtime → StandaloneServer)
./build.sh

# Or build individually
cd ImpunityCodeGenerator && ./build.sh   # outputs to bin/ and ImpunityUnity/Assets/Plugins/
cd ImpunityRuntime && ./build.sh         # builds Release + Debug, outputs to bin/Runtime/
cd ImpunityStandaloneServer && ./build.sh # outputs to bin/StandaloneServer/
```

All projects use `dotnet build -c Release`. The Unity project is opened via Unity Editor (version 6.3.9f1).

Run the test suite with `./test.sh` (see Tests below).

## Architecture

> In-depth manual for the distributed entity/channel system (annotations & ids, client↔server flow, subscriptions, persistence, client-authoritative, locks, temporal fields, local-only setters): [`docs/guides/DistributedEntities.md`](docs/guides/DistributedEntities.md).
>
> Companion manual for the connection & database model (local vs. remote connections, the connect handshake, the action request/reply system, the `Update()` loop, the document database, named locks, broadcasts): [`docs/guides/Connections.md`](docs/guides/Connections.md).
>
> Guide to schema versioning & migration (version+checksum guard, adopt-when-safe, and the implemented client-driven **data migration** flow: a higher-version client is *offered* a migration, runs it via raw name-addressed DB ops through `MigrationContext`, then commits — with server-side snapshot/restore, an ephemeral lock, idle timeout, and crash recovery): [`docs/guides/SchemaMigration.md`](docs/guides/SchemaMigration.md).
>
> Any format change (adopt *or* migration commit) unloads live memory: `UpdateFormat` calls `Live.UnloadAllEntities()` before `Live.SetFormat(...)`, because a live entity captures its `GameStateEntityType` at construction and sizes its property arrays from it, so nothing may survive a `SetFormat`. Persisted rows are untouched (unloading goes through `DestroyEntity`, which never writes to the DB) and reload on the next subscribe; replicated-only values and non-persisted channels are lost, as with the idle reaper. In-flight channel loads are discarded via `GameStateLive.FormatGeneration`.

- **Wire protocol**: 4-byte length prefix + 12-byte header + BSON body over TCP
- **Serialization**: UltraLiteDB's `BsonMapper` for documents; custom binary serializers (readonly structs) for distributed field types
- **Request/reply pattern**: Client sends `ClientAction` → server processes → server replies or pushes `ServerAction` messages
- **State replication**: Clients subscribe to *channels*; channels contain *entities* with typed *distributed fields* (`DistributedValue`, `DistributedArray`, `DistributedQueue`, `DistributedIntDictionary`, `DistributedStringDictionary`). Fields track dirty bits and serialize only deltas.
- **Entity locks**: server-enforced exclusive claims, with a FIFO waiter queue — releasing a lock hands it straight to the longest-waiting connection (`EntityLockGranted` push) rather than freeing it for a re-race. `UnlockEntity` flushes the entity's pending dirty fields before sending the release, which is what guarantees the next holder observes the previous holder's edits (guaranteed fields only — `SetUnguaranteed` writes leave the ordered path); this covers hand-rolled `TryLock`/edit/`Unlock` as well as the scoped form. `entity.RunExclusive(body, onComplete, timeout)` is the scoped form: it queues for the lock, runs the body, and releases on every exit path including exceptions. Note that queued waiters are served ahead of `TryLock` pollers, and a handoff raises `OnLocked` (not `OnUnlocked`) on other listeners, so retry loops built on `OnUnlocked` starve. Client code in `Client/Connection/ClientEntityExclusive.cs`; server queue in `GameStateEntity.Lock`/`Unlock`.
- **Transactions**: `entity.Transact(body, onComplete, maxAttempts)` is the optimistic sibling of `RunExclusive`: a read-modify-write committed as an `UpdateIfUnchanged`, with the body rerun against the winner's values on `ActionStaleData` (up to `maxAttempts` runs, default `ClientEntityManager.DefaultTransactMaxAttempts` = 5) and reported as `TransactResult` `Committed` / `Declined` (body returned false) / `Conflict` (out of attempts) / `Failed` (threw, entity gone, other error), once and never reentrantly. Client-only, no wire change. The manager keeps per-entity bookkeeping (`EntityTransactState`, keyed by entity instance): a FIFO of this connection's transactions, and a count of tracked in-flight writes (every plain `UpdateIfUnchanged`; the flush of changes pending when a body is due, sent as an ordinary update *with* a reply; and reliable sweep sends while a transaction waits on the entity). A conditional action riding a tracked write also counts until its own callback has run (`TrackConditionalAction` hangs a continuation on the action via the internal `GameStateActionBase.AfterCallback`, run by `CompleteOnClient` on every client-side resolution path, and which makes `HasCallback()` true so the server replies). So a rerun after a stale rejection, and the next queued transaction, see the application's reaction to the previous attempt's actions (e.g. a reserved inventory slot released). A body runs only when that count is zero, and since a reply always arrives after its own echo, `Get()` then returns this connection's own writes, so queued transactions never self-race. Pending changes being flushed first is what makes a decline safe: afterwards the dirty bits are the body's own, so a decline drops them (`GetPropertyBytes` into the shared buffer, then rewind) and resolves the body's conditional actions as `ActionConditionNotMet`. Except on client-authoritative entities, where `Set` already applied locally and the change is still sent. Entities with no manager/connection run the body offline and report at once. Unregistering an entity fails its active and queued transactions (`FailTransactionsForEntity` from `UnregisterEntity`). `Transact` is the documented default for contended writes (`maxAttempts: 1` for one-shot claims where losing means "don't"); `RunExclusive` when the body can't run twice, spans frames or holds the entity for a while; `UpdateIfUnchanged` / `DeleteIfUnchanged` are the bare primitives (no protection against this connection's own unechoed writes). Both primitives report `GuardedResult` `Applied` / `Stale` (null error) / `Failed` (error set) via `ClientEntityManager.GuardedCallback`, and their async wrappers fault only on `Failed`. A foreign lock is deliberately a failure everywhere, never waited for or retried: `TransactResult.Failed` / `GuardedResult.Failed` with `ActionBlockedByLock` (guide: "Optimistic writes and locks"). The body is `Func<TransactScope, bool>`: `tx.AddAction(action)` attaches a conditional action (same as `entity.AddConditionalAction`); a direct `Delete` / `DeleteIfUnchanged` / `UpdateIfUnchanged` on the entity from inside its own body throws (`ClientEntityManager.ThrowIfInTransactBody`, tracked by `TransactBodyEntity`) → `Failed`; `tx.Delete(guard, deleteData, onDeletedAction)` / `tx.ReplaceWith(guard, newObject, replaceData, onCreatedAction)` make the write a guarded delete/replace (guard required — an empty or foreign one throws in the body → `Failed`; mixing with field `Set`s or conditional actions → `Failed`; the conditional is tracked like a conditional action and resolved as skipped if never sent), and `tx.DependsOn(fields)` adds read-only fields to any write's guard (`SendGuardedNow`'s `extraGuard`). A successful delete/replace unregisters the entity before its reply, so `FailTransactionsForEntity` leaves a transaction with `RemovesEntity && AwaitingReply` to its reply (→ `Committed`) and fails only those queued behind it. Client code in `Client/Connection/ClientEntityTransact.cs`; guide: `docs/guides/DistributedEntities.md` §13 "Transactions"; tests: `Assets/Tests/Shared/TransactTests.cs` + `TransactScopeTests.cs` + `TransportSuite.TransactIncrementsFromTwoClients` / `TransactDeleteRerunsOnStaleGuard` (`--filter "Category=Transact"`).
- **Guarded delete and replace**: `entity.DeleteIfUnchanged(guard, deleteData, onComplete, onDeletedAction)`, `entity.ReplaceIfUnchanged(guard, newObject, replaceData, onComplete, onCreatedAction)` (`ClientEntityManager.ReplaceEntityIfUnchanged`: the standalone guarded replace, reporting `GuardedResult`; it and `tx.ReplaceWith` share `ResolveReplaceTarget` for the unique-name/channel rules and both end in `manager.CreateObject(..., replaceEntityId, replaceGuard, replaceData)`) and the raw `manager.CreateObject(..., replaceEntityId, replaceGuard)` carry a known-field-seq blob (the `UpdateIfUnchanged` format, built by `ClientEntityManager.BuildKnownSeqBlob`) on `DeleteEntityAction.KnownFieldSeqs` (`"xs"`) / `CreateObjectAction.ReplaceKnownFieldSeqs` (`"rxs"`). The server runs `ValidateGuardSeqs` before destroying anything (`GameStateLive.DeleteEntity` / the replace branch of `CreateObject`): stale → `ActionStaleData` on the wire (surfaced by `DeleteIfUnchanged` as `GuardedResult.Stale`), nothing changes, conditional skipped; a lock holder bypasses it; a foreign lock still answers false on the wire for a delete (which `DeleteIfUnchanged` turns into `GuardedResult.Failed` + `ActionBlockedByLock`) and `ActionBlockedByLock` for a replace. Fields are named by a typed `FieldGuard` (`Client/Connection/DistributedFields.cs`): every field type has a `Guard` property (`IDistributedField.Guard`, replacing the old raw `ulong Mask`), combined with `|`. A guard carries its entity instance plus the bit mask; `FieldGuard.MaskFor(entity, …)` is the one conversion to the internal `ulong`, and throws `ArgumentException` for an empty guard or one from a different entity instance (so a guard from another type, another entity, or even another client's copy can't silently guard the wrong fields); `|` across entities throws too. Internals (`BuildGuardBlob`, `TransactScope.GuardMask`/`DependsMask`, `SendGuardedNow`'s `extraGuard`) stay `ulong`. A replace guard supplies `replaceEntityId` itself when that is 0 (they must agree if both are given), and its entity must be registered with the manager. Guide: `docs/guides/DistributedEntities.md` §13 "Guarded delete and replace"; tests: `Assets/Tests/Shared/GuardedDeleteTests.cs` + `TransportSuite.GuardedDeleteAndReplaceAreStaleAfterAChange` (`--filter "Category=GuardedDelete"`).
- **Conditional actions**: `CreateObject` / `DeleteEntity` (and `entity.Delete`, `manager.CreateObject<T>`) take an optional trailing database action, sent in the same message and run only if the entity operation succeeded for this client. Updates carry them too: `entity.AddConditionalAction(action)` parks one on the entity (`ClientEntityConditionalActions.cs`) until its next update is built — per-frame sweep, `UpdateIfUnchanged(onComplete, action)`, or the flush before `Unlock` — forcing a reliable send, even an empty one; several pending travel as one `CompoundDatabaseAction` fanned back out via `ApplyResult`; the condition is "server applied the update"; an entity unregistered with actions pending fails them locally. This is the world ↔ inventory move: in a pickup race the live thread arbitrates, so only the winner's inventory insert runs. The server runs the entity op on the live thread, then queues `ConditionalDatabaseAction` (`GameStateServerActions.cs`), which runs the conditional on the DB thread and hops back to live via `QueueDBReply` to report it. That hop is what guarantees the conditional's reply arrives after the parent's. A skipped conditional replies `ActionConditionNotMet`. The conditional's reply rides a second correlation id (`ConditionalMessageId`, assigned in `RemoteGameConnection.SendMessage`; local connections use a non-zero marker). Allowed conditionals are opt-in via `CanRunConditionally()` (document actions + `CompoundDatabaseAction`). Not a transaction. A later *plain* DB action from the same client can commit before an earlier conditional (plain goes straight to the DB queue; the conditional waits for the live thread) — the guide's "Ordering against your other writes" says to use per-item docs or field-level merges (`unsetKeys` removes a top-level field) and hold same-key writes until the conditional's callback. Exactly-once callbacks: a method that returns always resolves its conditional (no-connection entity methods fire both callbacks synchronously; a disposed `RemoteGameConnection` fails both with `ClientConnectionBrokenError`); a method that *throws* never took it. Public `GameStateActionBase.SkipUnsent(reason)` / `FailLocally(error)` resolve an unsent action. Guide: `docs/guides/DistributedEntities.md` §11; tests: `Assets/Tests/Shared/ConditionalActionTests.cs` + the `TransportSuite` `Conditional*`/`UpdateActions*` cases (`--filter "Category=Conditional"`).
- **Update notes**: `entity.AddUpdateNote(bson)` (or `tx.Note(bson)` in a `Transact` body) parks a note that rides the entity's next update, like a conditional action (`Client/Connection/ClientEntityUpdateNotes.cs`, `PendingUpdateNotes`; `HasPendingUpdateExtras` = conditional action or note is what every "anything to send?" check uses). Wire: `UpdateEntityAction.Note`/`NoteSentServerMs` (`"nt"`/`"st"`) → `EntityUpdateMessageAction.Note`/`NoteSentServerMs`/`NoteFromRecipient` (`"nt"`/`"st"`/`"mn"`). Never stored. The server relays an empty update when it carries a note (`UpdateEntityProps`). `GameStateChannel.SendUpdateToListeners` keeps encode-once for un-noted updates; a noted one gets a second message for the writer with `NoteFromRecipient` set — the only per-recipient difference, and the only sender identity Impunity exposes (anything richer goes in the note). Client: `ApplyNotedUpdate` makes `entity.CurrentUpdateNotes` current during the apply (field `OnChanged`) and raises `OnUpdateNote` once per note after it. Notes accumulate like conditional actions (never last-wins): the client always sends a `BsonArray`, one element per `AddUpdateNote`, in the existing `"nt"` field, which the server relays untouched and the receiver unpacks; a null note throws `ArgumentNullException`. Client-authoritative writers get no echo. A note in a deleting/replacing transaction → `Failed`; a declined body's note is dropped. Guide: `docs/guides/DistributedEntities.md` §12 "Update notes"; tests: `Assets/Tests/Shared/UpdateNoteTests.cs` + `TransportSuite.UpdateNoteReachesEveryoneWithItsUpdate` (`--filter "Category=UpdateNote"`).
- **Cause envelope (events, notes, deletions)**: every "why" a receiver gets has the same three members: `Data`, `SentServerMs` (sender's `GetServerTime()` at the send; the server's clock when unstamped or server-made), `IsOwn` (this connection sent it). `EntityEvent` (+`Type`) in `OnEventTriggered`, `UpdateNote` in `OnUpdateNote`, `EntityDeletion` in `OnDeleted(EntityDeletion)` (structs in `Client/Connection/EntityEvents.cs` / `ClientEntityUpdateNotes.cs`). Wire: senders stamp `"st"` on `EventEntityAction`, `UpdateEntityAction`, `DeleteEntityAction`, `CreateObjectAction`; pushes carry `"st"` + `"mn"` (`FromRecipient`). `IsOwn` costs one extra message for the sender only (`GameStateChannel.SendToListenersMarkingSender`; everyone else shares one encode; a server-made delete is one shared message). A replace's cause is `replaceData` (`CreateObjectAction.ReplaceData`, `"rd"`; trailing parameter of `CreateObject`, third of `tx.ReplaceWith`), relayed as the replaced entity's delete data. `EntityEventEcho.ExcludeSender` still drops the sender's copy entirely. Guide: `docs/guides/DistributedEntities.md` §12 "One shape for every cause"; tests: `IntegrationTests` delete/event cases + `TransactScopeTests.ReplaceWith_Unchanged_Replaces`.
- **Update sequencing and unguaranteed delivery**: every entity sequence (`SendSeq`, `UpdateEntityAction.Seq`, server `RecvSeq`/`LastModSeq`/`OutSeq`, client `FieldRecvSeq`, and the known-field-seq guard blob, now `[fieldId][seq: uint LE]...[0]`) is a `uint`; advance with `ImpunityUtil.NextSeq` (never yields 0, which means "no seq") and compare with `ImpunityUtil.SeqIsNewer` (signed 32-bit difference). `GameStateEntity.ApplyProps` applies an update field by field and hands back the bytes to relay: a field the same writer already superseded is skipped, not stamped in `LastModSeq`, and left out of the relay; an update with no accepted field and no note is not relayed and does not advance `OutSeq`. A sender's delivery class travels as header flag `ImpunityMessageFlags.UNGUARANTEED` (set in `RemoteGameConnection.SendMessage` whichever path carries the message); `ImpunityServer.ClientMessageReceived` honours it only for an `UpdateEntityAction` with `MayBeUnguaranteed()` (no reply, guard, conditional action or note), which is what makes the relay unguaranteed too. Both transport interfaces have `MaxUnguaranteedMessageBytes` (`ImpunityConstants.MaxUnguaranteedMessageSize` = 1200): `RemoteGameConnection` and `ServerSideNetworkConnectionProxy.QueueMessage` send a larger unguaranteed message reliably. Tests: `IntegrationTests` `Sequence_*` (`Category=Sequence`; they move `SendSeq` by hand to fake late and long-running updates), `ImpunityTests/UnguaranteedDeliveryTests.cs` (`Category=Unguaranteed`; real loopback UDP, reads the internal `ImpunityTCPClient.UnguaranteedReceived`), `ServerSendBatchingTests.Unguaranteed_OverTheSizeLimit_IsSentReliably`. Design and remaining WebRTC stages: `docs/designs/WebRtcTransport.md`.
- **WebRTC transport (server, headless test client, and a WebGL client not yet proven in a Unity build)**: an optional unordered, zero-retransmit data channel beside each `/ws` WebSocket, for unguaranteed entity updates; design, stages and what is proven in `docs/designs/WebRtcTransport.md`. Signaling is WebSocket **text** frames handled inside `WebSocketController` and never seen by Impunity (binary frames are Impunity messages): the client sends `{"t":"offer","sdp":...}` and gets `{"t":"answer","sdp":...}` or `{"t":"unavailable","r":"disabled|unavailable|full|busy|failed"}`. The offer's candidates are stripped (the server learns the client's address from its first connectivity check); the answer carries the server's candidates plus `webrtc.public_address` if set. `WebRtcService` (singleton) loads libdatachannel via `LibDataChannelNative.TryLoad` (manifest tag + SHA-256 check; any failure just leaves `Available` false and logs one warning), probes the UDP port, enforces `max_peers`, routes native callbacks by peer/channel id, and ticks sessions every 500 ms. `WebRtcSession` is one peer + one channel: `IsOpen` drives the controller's `SupportsUnguaranteed`; `Send` drops when over a 16 KB buffered budget; it sends the header-only server `KEEPALIVE` after 1 s idle and closes after 5 s of silence or 15 s without opening; `Close` deletes native objects on the thread pool, never inside a callback. Every socket write in the controller takes `SendLock` (signaling replies come from another task). Datagram-path messages on both server transports (WebRTC and the TCP server's UDP) go to `OnUnguaranteedMessageRecieved` → `ServerSideNetworkConnectionProxy.ClientUnguaranteedMessageReceived`: no keepalive refresh, `UPDATE_ENTITY` only, established connections only. Config: `webrtc` object in `config.json` (`enabled`, `udp_port` 29656, `bind_address`, `public_address`, `max_peers` 256). The P/Invoke matches exactly libdatachannel v0.24.6 (`rtcConfiguration` differs between releases). Tests: `ImpunityTests/Host/WebRtc_Standalone.cs` (`--filter "Category=WebRtc"`, canned offer over a raw WebSocket; `StandaloneServerFixture.Launch(webRtcConfig, environment)`; `IMPUNITY_WEBRTC_RUNTIMES` redirects the loader). Client side: `IImpunityNetworkClient.OnUnguaranteedMessageRecieved` mirrors the server's split (`RemoteGameConnection.OnUnguaranteedNetworkMessageReceived`: no silence-deadline refresh, `ENTITY_UPDATE_MESSAGE` only; the TCP client's UDP path uses it). `ImpunityTests/Host/RtcWebSocketTestClient.cs` is a real WebSocket + libdatachannel peer (it compiles `LibDataChannelNative.cs` as source, which is why that file stays C# 9 with a block namespace) and the behavioural reference for the future WebGL bridge; it exposes counters (`ChannelSent`/`ChannelReceived`/`SocketEntityUpdatesReceived`/`SocketUnguaranteedSent`) and a `Blackhole` switch. `TransportSuite_StandaloneRtc` (in `Host/TransportSuite_StandaloneRtc.cs`) runs the transport battery over it plus the data-channel delivery and fallback cases; `WebRtcRefused_Standalone` covers a server with WebRTC off. Browser side: all of it is in `Assets/Plugins/ImpunityWebSocket.jslib` (offer on socket open, text-frame signaling, keepalive/silence/negotiation timers, one retry after 30 s that a successful open re-arms); C# (`ImpunityWebSocketClient`, WebGL branch) only gets `ImpunityRtcSetOpenCallback`/`CloseCallback`/`MessageCallback` and calls `ImpunityRtcSend(id, array, offset, length)` (0 sent, 1 dropped over budget, negative = no channel → socket). `ImpunityOptions.UseWebRtc` (default true) disables it; `MakeWebSocketClient(url)` / `MakeWebsocketRemoteConnection(url, …)` take a full `ws://`/`wss://` URL. Values inside the jslib's `$impunityWsState` object must survive being emitted as text by the build (plain arrays and numbers, no typed arrays). The WebGL branch compiles headlessly via `ImpunityRuntime/ImpunityUnityWebGLRuntime.csproj`; the jslib has only been run in a browser through a stand-in runtime, never in a real WebGL build.
- **Live-state inspection**: read-only queries `DescribeChannels(prefix)` / `DescribeChannel(name)` / `GetEntitySnapshot(id)` / `DescribeConnections()` on `BaseGameConnection` (actions 314–317, `InspectionActionBase` in `GameStateClientActions.cs`; result types + the server side in `Server/GameState/GameStateInspection.cs`, which made `GameStateLive`/`GameStateEntity`/`GameStateChannel` partial). Never load a channel to answer (`ActionNotFound`). A snapshot carries the create-format prop bytes plus per-field `LastModSeq`/time/last writer + its seq; the client decodes them with its own registry (`ClientEntityManager.DecodeSnapshot`, `GetFieldsAsBson`) and `CompareWithSnapshot` / `CheckSync` classify each differing field by seqs (`FieldSyncState`: `InFlightToServer` = dirty, or a client-authoritative owner's send newer than the newest of its writes the server applied; `InFlightToClient` = server `LastModSeq` newer than the client's `FieldRecvSeq`; `ChangedSinceSnapshot` = client seq newer than the snapshot's `OutSeq`; else `Mismatch`), with `BsonDiff` path lines. Client code `Client/Connection/ClientEntityInspection.cs`. `ImpunityOptions.AllowStateInspection` (default true) refuses the queries with `ActionBadRequest`. Guide: `docs/guides/DistributedEntities.md` §13 "Inspecting live state"; tests: `Assets/Tests/Shared/InspectionTests.cs` (`--filter "Category=Inspection"`).
- **Server threads**: TCP listener, UDP listener, network writer, connection keepalive sweep, DB worker, live state worker — coordinated via concurrent queues
- **Version checks**: two numbers, no feature negotiation and no backward compatibility before a game ships. `ImpunityConstants.ImpunityVersion` is the wire-protocol version: UDP discovery headers, `/info` + the HTTP finder, and the connect handshake (`EstablishConnectionAction.ImpunityVersion`, `"iv"`, checked in `ServerSideNetworkConnectionProxy` before the game-id/password checks; mismatch or missing → `ServerProtocolIncompatible` and close; local connections skip it; test seam `BaseGameConnection.ImpunityVersionOverride`). `GameStateFormatData.Version` covers game state *and* game rules: the game bumps it on either, and `GameStateServer.EstablishConnection` only lets equal version+checksum clients share a world. Tests: `ImpunityTests/ProtocolVersionTests.cs` + `Host/ProtocolVersion_Standalone.cs` (`--filter "Category=ProtocolVersion"`).
- **Keepalives / disconnect deadline**: `ImpunityOptions.ConnectionTimeoutMillis` (default 30s, floor `ImpunityKeepAlive.MinTimeoutMillis` = 10s, ≤0 disables) is a *server* setting handed to clients in `EstablishConnectResult.ConnectionTimeoutMillis`. Each end sends a header-only `KEEPALIVE` message (client type 104, server type 2; never deserialized, skipped in mapper registration) after a third of the window with no *guaranteed* send; any inbound message refreshes the receiver's monotonic `Stopwatch` timestamp. Server: `ImpunityServer.KeepAliveThreadMain` sweeps proxies, queues keepalives via the writer, and drops a silent client with `DropForSilence` (closes the transport without waiting for its send queue to drain, which faults a write stuck on a dead peer) → normal `ConnectionClosed` cleanup. Client: writer thread sends keepalives (`TryTake` bounded by the next due time; `Update()` on WebGL); `Update()` checks server silence. Every self-inflicted end (socket error, server close, silence) goes through `RemoteGameConnection.ConnectionLost`: fails in-flight actions with `ClientConnectionBrokenError`, closes the send queue, then on the main thread sets `Connected = false` and raises `OnNetworkError` once (only if `Connect` had completed). `Dispose()` never reports. Test seams: `ImpunityOptions.ConnectionTimeoutFloorMillis`, `RemoteGameConnection.KeepAlivesSuppressed`, `ImpunityServer.KeepAlivesSuppressed`. Guide: `docs/guides/Connections.md` §4; tests: `ImpunityTests/ConnectionKeepAliveTests.cs` + `Host/ConnectionKeepAlive_Standalone.cs` (`--filter "Category=KeepAlive"`); standalone legs run with `connection_timeout_ms` = 10s.
- **Send path (both ends)**: TCP has Nagle off (`NoDelay`) on both ends, so batching is done in the library. **Server:** the single network writer thread (`ImpunityServer.WriterThreadMain`) drains the global `PendingWrite` queue but never waits on a client's socket. Every message is encoded once into the writer's scratch buffer (`ImpunityServer.EncodeMessage`) and copied to an exact-size `byte[]`. A push (`ServerActionBase`) caches that array in `EncodedMessage`, so a fan-out to N listeners encodes once and shares the bytes (about 45% faster for 16 recipients in a quick benchmark). `ServerSideNetworkConnectionProxy.QueueMessage` appends to the connection's own `Outbound` queue (guarded by `OutboundLock`) and schedules it via `ImpunityServer.ScheduleWrite`. The writer only starts socket writes (`StartScheduledWrites`) when its queue runs dry, after `MaxSendsPerBatch` (64) sends, or after 64 KB queued, so a burst reaches each client as one write. At most one transport write is in flight per connection (`WriteInFlight`); each write's continuation takes the next batch (`TakeNextBatch`: up to `MaxBatchBytes` = 64 KB gathered into a pooled buffer; a lone message is written from its own array). Transports get several framed messages per `SendGuaranteedMessageAsync`; the WebSocket controller splits them on the length prefixes. Unguaranteed messages for a client with UDP skip the queue (`SendUnguaranteedNow`; the transport contract allows that alongside a write in flight); without UDP they are queued and sent reliably. A dead/non-reading client only backs up its own queue. `ProcessCloseConnection` doesn't block: it sets `CloseWhenFlushed` and the drain closes once the queue is empty; later sends are dropped. `ImpunityOptions.MaxSendBacklogBytes` (default 32 MB, ≤0 = unlimited, standalone `max_send_backlog_bytes`) counts queued + in-flight bytes; a client that would exceed it is dropped with a warning, and one message always fits an empty queue. Every server-side close (requested, silence, backlog) goes through `CloseTransport` (first caller wins, no-op if the peer already left, discards the queue). The WebSocket transport bounds its close handshake (2s, then `Abort`) so a send stuck on a dead peer can't keep `OnClientDisconnected` from firing. Tests that call `proxy.SendMessage` directly on an unstarted server must call `TcpServer.StartScheduledWrites()` in place of the writer thread. **Client:** `ImpunityTCPClient` writes through a 32 KB `BufferedStream`; `RemoteGameConnection`'s writer calls `IImpunityNetworkClient.Flush()` whenever `PendingSend` runs empty (WebSocket clients: no-op). Measured on loopback, `NoDelay` makes no latency difference (ACKs return in microseconds); it matters on real links where RTT exceeds message spacing. Guide: `docs/guides/Connections.md` §4 + §13; tests: `ImpunityTests/ServerSendBacklogTests.cs` (`--filter "Category=SendBacklog"`: fake `StallableClientContext` with held writes, plus a raw TCP client that handshakes and never reads) and `ServerSendBatchingTests.cs` (`Category=SendBatching`: one write per burst, 64 KB cap, encode-once shared array, UDP bypass).
- **Socket thread shutdown**: All socket listener threads use non-blocking checks (`Socket.Poll()` for UDP, `TcpListener.Pending()` for TCP accept, `ReceiveTimeout` for TCP stream reads) so they can poll `ImpunityLifecycle.ShuttingDown` and exit cleanly within ~1 second. Call `ImpunityLifecycle.CleanupAll()` at app shutdown to signal all threads to stop. This avoids a macOS deadlock where closing a socket from another thread does not reliably unblock a `Receive()` call.

## Conventions

- All client-facing APIs use callback delegates (`ImpunityCallback<T>`), with async/await and Unity coroutine yield extensions provided separately
- netstandard2.1 compatibility is required for all runtime code (Unity constraint)
- Public APIs have XML doc comments (`/// <summary>`), including every `…Async` / `…Yield` wrapper (one line naming the wrapped method and how the result and errors come back)
- Every `IDistributableValueSerializer<T>` declares `ValueSemantics` (`Immutable` / `Mutable`) alongside `ValueType`, and distributed field types put **no constraint on `T`** (the former `where T : IEquatable<T>` is gone — it excluded `ArraySegment<byte>`, which has an `Equals` overload but never declared the interface). `DistributedFieldPolicy.IsUnchanged` in `Client/Connection/DistributedFields.cs` is the single place a `Set` is decided to be a no-op: `Mutable` skips the comparison entirely so every `Set` marks the field dirty; `Immutable` compares via `EqualityComparer<T>.Default`. `Mutable` is for anything whose contents a caller can change without constructing a new value — `BsonSerializer<T>`, `BsonSmallSerializer<T>`, `BlobSerializer` — because `Get()` returns the field's own state, so a value modified in place and passed back to `Set` compares equal to itself and would otherwise be silently dropped. **When writing a serializer, `Mutable` is the safe answer**; declaring `Immutable` asserts the type has meaningful value equality, which the compiler no longer checks. Both properties are compile-time constants on a concrete serializer struct, so the branches fold away in specialized generics. The user-facing rule is *treat `Get()`'s result as read-only; copy, mutate the copy, `Set` the copy* — see the mutable-values section of `docs/guides/DistributedEntities.md`. Coverage: `Assets/Tests/Shared/MutableValueDirtyTests.cs` (`--filter "Category=MutableValue"`).
- Distributed entity types are annotated with `[DistributedEntity(typeId)]`. **Fields carry no attribute at all** — a field is distributed iff its type implements `IDistributedField` (instance fields only; `static`/`const` are ignored). The only field-level attribute is `[PersistAs("key")]`, which additionally stores the value. Wire ids are assigned by `DistributedFieldIds` per concrete type, walking the inheritance chain base-first and sorting by field name within each class, so ids never have to be coordinated across a class hierarchy. Adding or renaming a distributed field renumbers and is therefore a schema change (bump the version); reordering or moving declarations is free. The generator detects fields through the semantic model (`Compilation.GetTypeByMetadataName` + `AllInterfaces`), matching the runtime's reflection check exactly; it warns (`IMP4`) about a distributed field on a class with no `[DistributedEntity]`, and errors (`IMP5`) on `[PersistAs]` applied to a non-distributed field.

**Shared test sources** live in `ImpunityUnity/Assets/Tests/Shared/` and are compiled by BOTH the dotnet csproj (glob include) and Unity (asmdef `ImpunitySharedTests`, shows in the Play Mode tab) — the same source-sharing pattern the runtime uses. Portability rules for everything under `Shared/`:
- No `using UnityEngine` — `Harness/TestEnv.cs` holds the only `#if UNITY_5_3_OR_NEWER` (temp root, error log). The dotnet build enforces this at compile time.
- Internals are visible on both sides: to `ImpunityTests` through `ImpunityRuntime.csproj`'s `<InternalsVisibleTo>`, and to the `ImpunitySharedTests` asmdef through `Assets/Scripts/Impunity/AssemblyInfo.cs` (guarded by `UNITY_EDITOR`, so no DLL build carries it). - Tests are plain NUnit `[Test] async Task` methods driving the async API (`GameConnectionAsyncExt`); never `.Result`/`.Wait()`/`ConfigureAwait(false)` (Unity main-thread deadlock), and stay within Unity's NUnit 3.5 API surface (no `Assert.Multiple`).

- `Harness/SharedTestEntities.cs` holds the test entity types (all `partial`, codegen-dependent), including `TestVec3` — a portable stand-in matching Unity `Vector3Serializer`'s wire shape (CustomSmall, 12 bytes).

**Known gotchas preserved from the original suites:**
- `SubscribeToChannel*` discards the `createIfNeeded` instance — drive the *returned* channel. (`CreateObject*` keeps the caller's instance.)
- Non-client-authoritative `Set()` applies only on server echo — assert via `PumpUntil`, not synchronously.
- All `LocalGameConnection`s share the hard-coded `ConnectionKey` `"local_key"`, so the server treats them as the same client for lock ownership; tests needing two distinct local clients assign unique `ConnectionKey`s before connecting.
- Known intermittent issue under full-suite load (~1 in 6–10 full runs): a second subscriber's `SubscribeChannelAction` over TCP occasionally gets no reply within `ActionTimeoutMillis` — tracked as a library race to investigate, not a harness bug.
- A backlog limit set on the test server applies to every client, the one sending included: `ServerSendBacklogTests.NonReadingTcpClient_OverBacklogLimit_IsDropped` sends its broadcasts a window at a time and waits for them to come back, because sending them all at once got the broadcaster itself dropped whenever the machine was busy.
- Tests that need a scope to stay open while another client queues behind it use the `TaskCompletionSource` "gate" pattern (see `ExclusiveScopeTests`): the body awaits the gate, and the test completes it to release the lock. To exercise the flush-before-unlock ordering the body must write *after* the gate — writing before it lets the ordinary per-frame sweep flush the update while the test pumps, which hides the bug.
